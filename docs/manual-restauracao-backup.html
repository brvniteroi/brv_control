Manual de Restauração do Backup

BRV Control · control.brvniteroi.com.br · versão de 12/11/2026

Para que serve este manual: se o servidor da HostGator ou o banco de dados (Supabase) perderem os dados, este passo a passo explica como recolocar tudo no ar usando as cópias de segurança. Foi escrito para ser seguido com calma, de cima para baixo, sem precisar entender de programação. Em qualquer passo, você pode pedir ajuda ao Claude Code (veja a página "Como pedir ajuda").

Regra de ouro Nunca apague, mova ou sobrescreva as cópias de segurança (a pasta D:\backups-brv) antes de ter certeza de que tudo foi restaurado e está funcionando. Ao restaurar o banco, prefira sempre um projeto novo e vazio no Supabase, em vez de escrever em cima do projeto estragado.

1. Onde estão as cópias de segurança

O backup roda sozinho no computador da empresa (DESKTOP-PKGLS0I), de segunda a sexta às 9h (tarefa "BRV Control - Backup" do Agendador de Tarefas do Windows). O computador precisa estar ligado; se estiver desligado às 9h, o backup roda assim que ligar.

Conferência semanal (1 minuto)

Abra D:\backups-brv\backup.log e veja se as últimas linhas dizem OK control e TERMINOU sem problemas com a data de hoje ou do último dia útil. Veja também se existe um arquivo .dump recente e com cerca de 14 MB (um arquivo de poucos KB está quebrado).

4. Caso A – Restaurar o servidor da HostGator

O servidor guarda o aplicativo (as páginas do site), a pasta api (envio de fotos e e-mail de avaliação) e as fotos. O aplicativo é refeito pelo GitHub; as fotos voltam das cópias.

Passo 1 – Garantir a conta FTP e o subdomínio (só se a conta foi recriada)

  • No cPanel da HostGator, o subdomínio control.brvniteroi.com.br precisa existir, com o certificado SSL (HTTPS) ativo.
  • Deve existir uma conta FTP presa à pasta desse subdomínio (a raiz da conta FTP é a raiz do aplicativo).
  • Se usuário ou senha do FTP mudaram, atualize os segredos FTP_SERVER, FTP_USERNAME e FTP_PASSWORD no GitHub e as mesmas três linhas no .env do PC.

Passo 2 – Reenviar o aplicativo e a pasta api (deploy)

  1. Abra github.com/brvniteroi/brv_control > aba Actions.
  2. Clique em "Deploy (control.brvniteroi.com.br)" > botão Run workflow > Run workflow.
  3. Espere ficar verde (cerca de 2 a 4 minutos). Isso compila o site, gera o config.php a partir dos segredos e envia tudo por FTPS.
  4. Abra https://control.brvniteroi.com.br e confira que a tela de login aparece.
Se o deploy ficar vermelhoAbra a execução, veja a linha com erro. "Falta a variável..." = algum segredo do GitHub está vazio. Erro de login no FTP = senha do FTP errada.

Passo 3 – Devolver as fotos

O deploy não traz as fotos de volta. Use um programa de FTP, como o FileZilla (gratuito, filezilla-project.org):

  1. Conexão: servidor ftp.brvniteroi.com.br (o mesmo do FTP_SERVER), usuário e senha do FTP, porta 21, criptografia "Exigir FTP explícito sobre TLS". Se aparecer aviso de certificado, aceite (o certificado é da HostGator).
  2. Lado esquerdo (seu computador): abra D:\backups-brv\fotos.
  3. Lado direito (servidor): abra a pasta api/uploads (se não existir, o deploy do passo 2 a cria).
  4. Selecione tudo dentro de fotos (as pastas de anos como 2026, a pasta placas etc.) e arraste para api/uploads. Pode levar de alguns minutos a algumas horas, conforme o tamanho.
  5. Não apague nem substitua o arquivo .htaccess de dentro de api/uploads: ele é do deploy e protege a pasta. Se perguntar "arquivo já existe", escolha pular os que já existem.

Fotos antigas do Field Control (pasta api/uploads/fc): no PC da empresa, abra o PowerShell na pasta do projeto e rode:

cd D:\brv-control
Remove-Item scripts\field-control\dados\fotos_enviadas.ndjson
node --env-file=.env scripts/field-control/enviar-fotos.mjs
ImportanteO Remove-Item acima é necessário: esse arquivo é a "lista do que já foi enviado". Se ele ficar, o programa acha que tudo já está no servidor e pula todas as fotos.

Passo 4 – Aplicativo Android (só se a pasta app/ sumiu)

No GitHub > Actions > "APK do app de campo (Android)" > Run workflow. Ele recompila e republica o aplicativo em /app/brv-control.apk. Precisa dos segredos ANDROID_* e GOOGLE_SERVICES_JSON_BASE64.

Passo 5 – Testar

5. Caso B – Restaurar o banco de dados (Supabase)

O arquivo .dump é uma "fotografia" completa do banco no dia: todas as tabelas do sistema (esquema public), as regras de acesso e permissões e os logins dos usuários (esquema auth, com as senhas já criptografadas; os usuários continuam com as mesmas senhas).

O que o .dump NÃO trazAs Edge Functions, os segredos, as configurações do Authentication e a lista de tabelas do Realtime. Estes passos recriam cada um deles.
Dumps antigosOs arquivos anteriores a 12/11/2026 foram feitos sem as permissões de acesso. Se só tiver um desses, após restaurar siga a conferência de segurança do passo 10 com muito cuidado. Os dumps novos já trazem tudo.

Antes de começar: preparar o computador

  • No PC da empresa, o PostgreSQL 17 já está instalado em C:\PostgreSQL17\bin (é de lá que vêm o pg_dump do backup e o pg_restore desta restauração). Em outro computador, instale o PostgreSQL 17 e marque apenas "Command Line Tools".
  • Abra o PowerShell. Todos os comandos abaixo são para o PowerShell.

Passo 1 – Criar um projeto novo no Supabase

  1. Entre em supabase.com/dashboard > New project.
  2. Nome: brv-control. Região: South America (São Paulo). Defina uma senha do banco forte e anote em papel (você vai precisar dela daqui a pouco).
  3. O plano gratuito permite 2 projetos ativos. Se já houver 2, pause ou exclua um (por exemplo o do BRV Equipamentos, que será desligado, ou o projeto estragado depois de salvar o que puder dele).
  4. Espere o projeto terminar de criar (1 a 2 minutos). Anote o identificador do projeto (os 20 caracteres no endereço, tipo abcdefghijklmnopqrst).

Passo 2 – Ligar as extensões

No projeto novo: Database > Extensions. Procure e ative as três (deixe o esquema extensions): pg_net, pg_trgm e unaccent.

Passo 3 – Pegar o endereço de conexão

  1. No projeto novo, clique em Connect (topo da tela) > Session pooler (porta 5432).
  2. Copie o endereço. Ele tem esta forma: postgresql://postgres.IDENTIFICADOR:[YOUR-PASSWORD]@aws-...pooler.supabase.com:5432/postgres
  3. Troque [YOUR-PASSWORD] pela senha do passo 1. Se a senha tiver símbolos como @ # / : ?, eles precisam ser codificados (@ vira %40, # vira %23, / vira %2F). Senha só com letras e números evita o problema.

No PowerShell, guarde o endereço numa variável (ele fica só na memória daquela janela) e aponte para o programa:

$env:Path += ";C:\PostgreSQL17\bin"
$url = "COLE_AQUI_O_ENDERECO_COMPLETO_COM_A_SENHA"
$dump = "D:\backups-brv\banco\control\control-AAAA-MM-DD.dump"   # troque pela data do arquivo mais recente

Passo 4 – Conferir o arquivo antes de usar

pg_restore --list $dump | Select-Object -First 12

Deve listar o cabeçalho (Archive created at...) e as primeiras linhas, sem mensagem de erro. Se disser "file is not valid" ou parecido, o arquivo está quebrado: tente o dump do dia anterior.

Passo 5 – Restaurar os usuários (logins)

Vem primeiro, para que as tabelas do sistema encontrem seus usuários:

pg_restore --no-owner --data-only -n auth -t users -t identities -d $url $dump

Não deve aparecer erro. Se o comando terminar sem mensagem, deu certo.

Passo 6 – Restaurar as tabelas do sistema

pg_restore --no-owner -n public -d $url $dump

Demora de 1 a 5 minutos. É normal aparecer poucas mensagens de erro como schema "public" already exists (o esquema já existe no projeto novo). Qualquer outro erro: anote o texto e peça ajuda (não repita o comando sem conferir, pois duplicaria dados).

Passo 7 – Religar as atualizações ao vivo (Realtime)

No Supabase: SQL Editor > New query > cole e clique em Run:

ALTER PUBLICATION supabase_realtime ADD TABLE
  public.attachments, public.board_orders, public.print_jobs,
  public.service_order_tags, public.service_orders, public.tasks,
  public.technician_locations, public.technician_presence,
  public.workshop_orders;

Passo 8 – Apontar o aviso do técnico para o projeto novo

A tabela de configuração dos avisos (push) guarda o endereço do projeto antigo. No SQL Editor, troque NOVO_ID pelo identificador do projeto novo:

UPDATE public.push_config
   SET function_url = 'https://NOVO_ID.supabase.co/functions/v1/notificar-tecnico';

Passo 9 – Conferir se os dados voltaram

No SQL Editor:

select 'usuarios' as item, count(*) from auth.users
union all select 'clientes', count(*) from public.customers
union all select 'ordens de servico', count(*) from public.service_orders
union all select 'maior numero de OS', max(number) from public.service_orders;

Compare com o sistema que você conhecia: em 12/11/2026 eram 11 usuários e a numeração das OS passava de 17.380. O número de usuários e de OS deve ser igual ou muito próximo do último dia do backup.

Passo 10 – Conferência de segurança (não pule)

No SQL Editor, rode:

-- 1) Deve dar 0: visitantes sem login não podem ler nenhuma tabela
select count(distinct table_name) as tabelas_abertas_ao_publico
  from information_schema.role_table_grants
 where table_schema = 'public' and grantee = 'anon';

-- 2) Deve dar nenhuma linha: toda tabela precisa ter RLS ligado
select c.relname as tabela_sem_rls
  from pg_class c join pg_namespace n on n.oid = c.relnamespace
 where n.nspname = 'public' and c.relkind = 'r' and not c.relrowsecurity;
Se a consulta 1 mostrar um número maior que 0As permissões não voltaram completas e o banco ficou mais aberto que o normal. Rode já, no SQL Editor: 
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon;
REVOKE ALL ON ALL SEQUENCES IN SCHEMA public FROM anon;
e peça ajuda ao Claude Code para conferir as funções (a página pública /avaliar, /placa e /orcamento-placa usam funções que devem continuar liberadas para visitantes: avaliacao_ver, avaliacao_enviar, placa_acompanhamento, placa_orcamento_ver e placa_orcamento_aprovar).

Passo 11 – Publicar as Edge Functions

No projeto novo: Edge Functions > Deploy a new function (ou "Via Editor"). Crie as quatro, com exatamente estes nomes, colando o conteúdo do arquivo supabase\functions\NOME\index.ts do projeto (D:\brv-control):

NomeVerify JWTSegredos que ela usa
gerenciar-usuariodeixar o padrão do painel (ligado)nenhum extra
apoio-tecnicoLigadoGEMINI_API_KEY
notificar-tecnicoDESLIGADOFIREBASE_SERVICE_ACCOUNT
consultar-osDESLIGADOEQUIPAMENTOS_SEGREDO

Depois, em Edge Functions > Secrets, crie os segredos da tabela (veja a seção 2 para saber de onde vem cada valor).

Passo 12 – Apontar o sistema para o projeto novo

O endereço e as chaves mudaram. Pegue-os em Project Settings > API do projeto novo (Project URL e a chave anon / publishable; nunca use a service_role no GitHub).

  1. GitHub > Settings > Secrets and variables > Actions: atualize VITE_SUPABASE_URL e VITE_SUPABASE_ANON_KEY.
  2. No .env do PC da empresa e do de casa: VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY e BACKUP_DB_URL_CONTROL (para o backup continuar funcionando!).
  3. Rode o Deploy (Actions > Deploy > Run workflow), como no Caso A, passo 2.
  4. Servidor da loja: o agente da impressora guarda SUPABASE_URL e SUPABASE_ANON_KEY no arquivo .env da pasta dele (C:\brv-agente-impressora\agente-impressora); atualize os dois e reinicie a tarefa "BRV Control - Impressora". O login do agente (impressora@...) é restaurado junto com os usuários.
  5. Se o BRV Equipamentos ainda estiver em uso: o control-proxy.php dele aponta para a função consultar-os; atualize o endereço.
  6. Supabase > Authentication > URL Configuration: Site URL = https://control.brvniteroi.com.br, e repita as demais opções do projeto antigo (URLs de redirecionamento etc.).

Passo 13 – Testar

☐ Entrar com seu usuário e senha de sempre.   ☐ Abrir uma OS, um cliente e uma placa.   ☐ Criar e excluir uma atividade de teste.   ☐ Entrar com um técnico no celular e ver a agenda (todos terão que entrar de novo: as sessões antigas não existem mais).   ☐ Criar uma atividade de hoje para um técnico com o app fechado e ver se chega o aviso.   ☐ Abrir um link público de avaliação.   ☐ Rodar o backup e ver se dá OK: node scripts/backup/backup.mjs --so-banco

Se só algumas informações foram apagadas por engano

Não é preciso restaurar tudo. O projeto atual continua funcionando; recupere só a tabela afetada, gerando um arquivo de texto legível a partir do dump de antes do erro (exemplo para a tabela de clientes):

pg_restore --data-only -n public -t customers -f "$env:USERPROFILE\Desktop\clientes.sql" $dump

Esse arquivo não deve ser rodado inteiro em cima do banco atual (duplicaria registros). Entregue-o ao Claude Code para extrair e reinserir só as linhas que sumiram.

6. Se o computador da empresa for perdido

Sem o computador, as cópias de segurança também se perdem, a menos que exista a cópia externa (Drive ou HD) que ainda precisa ser configurada. Para voltar a ter backups em outro computador:

  1. Instale o Git, o Node.js 24 e o PostgreSQL 17 (só "Command Line Tools").
  2. Baixe o código: git clone https://github.com/brvniteroi/brv_control.git D:\brv-control e rode npm install na pasta.
  3. Copie o .env do PC de casa para D:\brv-control. Confira que tem BACKUP_DB_URL_CONTROL, FTP_SERVER, FTP_USERNAME e FTP_PASSWORD.
  4. Teste manualmente: node scripts/backup/backup.mjs. Deve terminar com "TERMINOU sem problemas".
  5. Agende (PowerShell como administrador), de segunda a sexta às 9h: 
    $node = (Get-Command node).Source   # no PC da empresa é D:\node.exe
$acao = New-ScheduledTaskAction -Execute $node -Argument "scripts\backup\backup.mjs" -WorkingDirectory "D:\brv-control"
$gatilho = New-ScheduledTaskTrigger -Weekly -DaysOfWeek Monday,Tuesday,Wednesday,Thursday,Friday -At 9:00
$config = New-ScheduledTaskSettingsSet -StartWhenAvailable
Register-ScheduledTask -TaskName "BRV Control - Backup" -Action $acao -Trigger $gatilho -Settings $config
  6. Copie também a pasta android-assinatura de volta (pen drive, Google Drive ou PC de casa).
PrevençãoPeça ao Claude Code para configurar a cópia externa dos backups (Google Drive ou HD) e copie, de tempos em tempos, a pasta scripts\field-control\dados\fotos (fotos antigas do Field, 14 GB) para um HD externo.

7. Como pedir ajuda ao Claude Code

Abra o Claude Code na pasta do projeto (D:\brv-control) e escreva algo assim, trocando o que for preciso:

"Perdi o banco do Supabase (ou: perdi os arquivos da HostGator). Leia o CLAUDE.md e o docs/manual-restauracao-backup.pdf (ou .html) e me ajude a restaurar a partir do backup mais recente em D:\backups-brv. Estou no passo ___ e apareceu este erro: ___"

Cole o texto completo da mensagem de erro. Nunca cole senhas e chaves em lugares públicos; no Claude Code, prefira dizer onde a chave está em vez de colá-la.

8. Glossário rápido

Dump (.dump)Arquivo com uma cópia completa do banco de dados em um dia.
pg_dump / pg_restoreProgramas do PostgreSQL: o primeiro cria o dump (usado pelo backup); o segundo devolve o dump para um banco.
SupabaseServiço onde ficam o banco de dados, os logins e as funções do sistema.
HostGatorServidor do site (control.brvniteroi.com.br) e das fotos.
Session poolerTipo de endereço de conexão do Supabase usado pelo backup e pela restauração.
DeployPublicar o sistema no servidor. Acontece sozinho ao enviar mudanças ao GitHub, ou manualmente em Actions > Run workflow.
Segredo (secret)Senha ou chave guardada fora do código, no GitHub ou no Supabase.
RLSRegra do banco que decide quem pode ver cada linha; é o que impede visitantes de ler dados.
Edge FunctionPequeno programa que roda dentro do Supabase (avisos, criação de usuários, apoio técnico).
